## 0. TL;DR

1. **The current server cannot reach your instance, and it leaks the API key.** It is an unmodified fork of
   `calcom/cal-mcp` (abandoned since 2025-05-22): 16,864 lines of tools generated by
   `@buildwithlayer/openapi-to-tools`, every URL hard-coded to `https://api.cal.com/v2/...`, stdio only. The
   library writes `CAL_API_KEY` into every tool's JSON schema as a `default`, so **`tools/list` hands your raw
   Cal.com key to the client and the model**. 86 of the 167 `--all-tools` tools aren't in Cal.diy's API (81 of
   them are organization/team endpoints that Cal.diy removed), and 16 tool names collide and silently overwrite
   each other.
2. **Cal.diy has exactly one API — API v2 — and it is not deployed on book.techmavie.digital.** Cal.diy removed
   API v1 and every EE feature (teams, orgs, routing forms, workflows, insights, SSO). API v2 (`apps/api/v2`,
   NestJS) is a *separate service* that needs Redis. Your fork's CI only builds the web image, and
   `https://book.techmavie.digital/api/v2/*` returns the Next.js 404 page today. → **Phase 0 (with you): build and
   deploy Cal.diy API v2** (CI image in your fork, Redis + API container, nginx `location /api/v2/`).
3. **API research (Cal.diy @ `366c88e`, 2026-10-23):** 121 documented operations. Auth is
   `Authorization: Bearer cal_<32 hex>` (Settings → Developer → API Keys), and **no license key** is needed. The
   versioned resources need the right `cal-api-version` header, otherwise they silently fall back to the old
   2024-04-15 shapes: bookings `2024-08-13`, event types `2024-06-14`, schedules `2024-06-11`, slots `2024-09-04`.
   Rate limit: 120 requests/min per key.
4. **Rebuild on the Plausible v2 skeleton** (your newest MCP, live-verified 2026-10-08). It brings per-request
   server/transport, the hosted/self-hosted/stdio auth modes, the key-service resolver, the SSRF guard, gated
   analytics, server card, diagnostics, the deploy workflow and node:test + e2e smoke. Almost all of the
   infrastructure carries over with renames; the Cal-specific client and tools are new.
5. **mcp-key-service** gets a `calcom` connector (API URL + API key + access level). Clients use
   `https://mcp.techmavie.digital/calcom/mcp/usr_…`.
6. **39 hand-written, LLM-friendly tools replace 167 generated ones.** They cover 51 of the 121 endpoints. 45 are
   not applicable to an API-key assistant (deprecated Platform, OAuth plumbing, team-only, key rotation) and 25 are
   deferred. Inputs are timezone-aware (local time + IANA zone → UTC). Outputs are agenda-style markdown in your
   timezone. Bookings get an availability pre-check, and there is a booking summary computed client-side (Cal.diy
   has no Insights). Errors carry actionable hints, and 429s are retried.
7. **Read-only by default.** Access level `bookings` unlocks booking actions; `full` also unlocks configuration
   changes (event types, availability, webhooks, profile). The 7 destructive tools also need `confirm: true`.

### 3.3 Credential handling in the MCP

The key service stores fields verbatim (no trim, no defaults; a cleared optional field may arrive as `''`).
`normalizeConnection()` therefore:

- **API key**: trim; strip a pasted `Bearer ` prefix; warn (don't fail) if it doesn't start with `cal_`, since an
  instance may set a custom `API_KEY_PREFIX`.
- **API URL** → base URL used for `${base}/<resource>`:
  - blank → `https://api.cal.com/v2` (Cal.com Cloud)
  - host `api.cal.com` with no path → `…/v2`
  - path ending in `/v2` (`/api/v2`, `/v2`, `/cal/api/v2`) → used as is
  - no path (e.g. `https://book.techmavie.digital`) → `…/api/v2`; API v2 serves `/api/v2/*` by default, so this
    works both behind a path-routed nginx and on a dedicated API host
  - a pasted endpoint URL (`…/api/v2/bookings`) → trimmed back to the base
  - http(s) only, no credentials / query / fragment
- **Access**: `read` (default; also `''`, `no`, `readonly`) · `bookings` (`booking`) · `full` (`all`, `admin`,
  `write`, `yes`, `true`); unknown → `read` + a warning shown by `hello`.
- `isCloud` = host is `api.cal.com`; used only for hints (Cloud has more features than Cal.diy).
- **SSRF guard** (hosted + self-hosted HTTP, not CLI): Plausible's connect-time lookup guard and IP-literal check,
  with `ALLOW_PRIVATE_CALCOM_HOSTS` as the allowlist; `redirect: 'manual'` on every upstream call.

Resolver mapping (unchanged from Plausible): 401/404/`valid:false` → `invalid_key` → HTTP 403; 400/403/5xx/timeout →
`service_unavailable` → 503; non-JSON → `malformed_response` → 502. Successes cached 60 s, in memory, keyed by the
`usr_` key. Only `usr_xxxxxxxx…` prefixes are logged.

### 4.4 Tool conventions

- `server.registerTool(name, { title, description, inputSchema, annotations }, handler)`; snake_case, no prefix
  (matches mcp-github / Plausible; clients namespace tools per server). Server `instructions` give the
  booking flow: `list_event_types` → `get_available_slots` → `create_booking`; uids identify bookings; times
  are shown in the account timezone; ask before destructive tools.
- zod `.describe()` on every parameter, with examples; enums for statuses, triggers, weekdays, location types,
  presets. `cal-api-version`/`Authorization` are **never** tool inputs.
- **Time**: inputs accept ISO with offset (`2026-10-27T15:00:00+08:00`), UTC (`…Z`), or local wall time
  (`2026-10-27 15:00`) + `time_zone` (default = profile timezone, cached from `/v2/me`). Conversion uses
  `Intl.DateTimeFormat` (DST-safe, no dependency) and rejects non-existent local times (DST gaps) with a clear
  message. Presets (`today`, `this_week` …) are computed in the display timezone. Outputs always name the zone.
- **Output**: `format: 'markdown' (default) | 'json'`. Markdown = header (range, zone, filters) + agenda/table +
  next-step hints. JSON = normalised objects (uid, start/end ISO UTC + local, status, attendees, …).
- **Errors**: one `runTool()` wrapper → always `isError: true`. Cal errors → message + hint:
  validation `details.errors[]` flattened to `field: constraint`; 401 → "key invalid/expired — create a new one at
  Settings → Developer → API Keys"; 403 → not your resource; 404 JSON → not found (or endpoint missing on an older
  Cal.com version); **404 HTML → "this URL serves the Cal web app, not API v2" (link to docs/CALDIY-API-V2.md)**;
  429 → rate limited (120/min), seconds until reset; 3xx → "use the final https URL".
- **Client**: `AbortSignal.timeout`, 429 retry ×2 honouring `X-RateLimit-Reset-*` / `Retry-After` (≤ 10 s, else
  1/2 s backoff), `redirect: 'manual'`, SSRF-guarded dispatcher in HTTP mode, typed
  `CalApiError { status, code, message, details, endpoint }`, `User-Agent: mcp-calcom/2.0.0`, never logs keys.

## 10. Risks & mitigations

| Risk | Mitigation |
|---|---|
| API v2 build is heavy (full monorepo) | Same GitHub-hosted runner prep as your web build (disk cleanup, `MAX_OLD_SPACE_SIZE`); cached layers |
| API v2 shares the VPS with Cal web, the MCP servers and the key service | `mem_limit` on `calcom-api`; `ENABLE_SLOTS_WORKERS=false` if memory gets tight; watch `docker stats` after deploy |
| Redis `?tls=true` in production | Plan A URL-fragment trick, Plan B CI patch (§5) |
| Web / API version drift after "Sync fork" | Build both images from the same commit; deploy the same `sha-` tag |
| Paid (HitPay) event types: API bookings skip the checkout page | `create_booking` warns when the event type has a price and suggests sharing the booking URL instead; behaviour confirmed in the live check |
| API bookings have real side effects (emails, calendar events) | Tool descriptions say so; live write tests only on a hidden test event type, with your go-ahead |
| Exposing API v2 publicly widens the booking stack's surface | All user data needs a key; Redis rate limiting; production mode (no Swagger UI); optional nginx allowlist for `/api/v2/` if only the MCP (same VPS) should reach it; the source address its requests arrive from is checked in Phase 0 |
| Rate limit 120/min per key | 429 retry; summary tool caps pages; parallel calls bounded |
| Timezone mistakes | Central conversion + DST tests; outputs always name the zone; pre-flight slot check |
| Cal.com Cloud behaviour differs | Same versioned endpoints; best-effort, documented as untested |
| Upstream Cal.diy changes endpoints/shapes | Version map in one file; smoke stub mirrors the pinned spec; `get_instance_info` reports API errors clearly |
| 60 s credential cache delays revocation | Same trade-off as all sibling MCPs; documented |

## 11. Out of scope (candidates for later)

Team / org / routing-form / workflow tools (Cloud-only). Slot reservations. Unified-calendar event writes
(Google-only). Selected/destination calendar changes. Private-link updates. Adding a non-primary attendee via
`POST …/attendees` (`add_booking_guests` covers it). OAuth for the MCP itself. Platform / managed users.
A Smithery endpoint. npm publishing.
